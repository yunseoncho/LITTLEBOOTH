# 보안 계획 — iOS 앱 v1

기준: OWASP MASVS(STORAGE · CRYPTO · AUTH · NETWORK · PLATFORM · CODE · PRIVACY) L1 전 항목 + L2 중 STORAGE·CRYPTO·PRIVACY.
상태 표기: ✅ 구현+테스트 / 🟡 구현했으나 **실기기 미검증** / 📝 계획(출시 전 필수는 P0)

> 이 앱의 가장 큰 보안 결정은 **"가진 데이터를 줄이는 것"**이다. 서버·계정·분석 SDK·AI 호출을 없애서 서버 침해, 키 유출, 계정 탈취, 추적 위험이 구조적으로 없다(ADR-0004·0005).

## 지키려는 것
판매 기록(금액·시각), 함께 부스를 낸 사람의 이름, 위탁 상품과 원가, (이후) 송금 계좌·링크, 그리고 이 모든 것을 푸는 DB 키.

## 일부러 하지 않는 것 (비목표)
- **탈옥 탐지:** 우회가 쉽고 오탐이 사용자에게 피해를 준다.
- **인증서 고정(pinning):** v1은 네트워크가 없다. 서버를 도입하면 그때 비용 대비 효과를 따진다.
- **서버 쪽 계정 보안:** 계정이 없다.

## 한계 (솔직하게)
1. **실기기에서 검증하지 못했다.** 이 계획의 🟡 항목(SQLCipher, 파일 보호, Face ID, 앱 전환기 블러)은 코드와 네이티브 설정(prebuild 산출물)까지만 확인했다. TestFlight 실기기 점검표(아래)를 통과해야 ✅가 된다.
2. **앱 잠금은 화면 보호이지 키 보호가 아니다.** DB는 앱 시작 시 열리고, 잠금 화면은 UI를 가린다. 기기를 탈취당한 공격자가 앱 메모리에 접근하는 수준의 위협은 막지 못한다. 더 강하게 하려면 DB 키를 `requireAuthentication`으로 보호해 열 때마다 생체 인증을 요구할 수 있으나, 현장 판매 속도와 맞바꿔야 한다.
3. SQLCipher 키는 사용 중 메모리에 존재한다(모든 클라이언트 측 암호화의 공통 한계).
4. 암호화 라이브러리 사용에 따른 **미국 수출 규정(암호화 질문)**은 법무 확인이 필요하다(아래 점검표).

## 출시 전 점검표
**코드·빌드**
- [ ] 릴리스 빌드에서 `cipher_version` 존재 확인(실기기 로그 또는 테스트 빌드 화면)
- [ ] 릴리스 빌드에서 암호화 끈 채 실행하면 앱이 열리지 않는지(fail closed) 확인
- [ ] DB 파일을 기기에서 꺼내(탈옥 없이 가능한 방법: 개발 빌드 + 파일 공유) 헤더가 평문 SQLite가 아닌지 확인
- [ ] Face ID 거부·미등록·암호만 있는 기기·잠금 후 복귀 시나리오
- [ ] 앱 전환기 스냅샷이 흐리게 보이는지
- [ ] 암호화 백업 내보내기/가져오기 구현 및 복원 테스트 (P0)
- [ ] `npm audit` 심각 이슈 0, gitleaks 통과
- [ ] Xcode Privacy Report로 필수 이유 API 선언 점검(앱 단 매니페스트는 추적·수집 없음만 선언, 라이브러리 매니페스트는 각 패키지가 포함)

**스토어·법무**
- [ ] 앱 개인정보 라벨: "데이터 수집 안 함"(앱 기능과 실제 동작 일치 확인)
- [ ] 개인정보 처리방침 URL(landing/privacy.html) 게시, 한·영 외 일·중 번역 검수
- [ ] 수출 규정 암호화 질문 답변 확인(SQLCipher는 OS 제공이 아닌 오픈소스 암호화)
- [ ] 국가별 개인정보 법규 검토: 한국 개인정보 보호법, 일본 APPI, 중국 PIPL, 미국(캘리포니아 CCPA 등), EU GDPR — **개발자가 데이터를 수집하지 않는 구조**라서 의무가 줄어드는지는 전문가 확인 필요
